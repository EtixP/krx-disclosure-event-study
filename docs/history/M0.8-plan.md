# M0.8 plan — Official-source and production-license feasibility

**Plan status:** independently approved; implementation not started  
**Date:** 2026-10-03  
**Initial cohort:** buyback only  
**Implementation status:** not started

## Why this milestone exists

M0.7 proved that the frozen event-study CSVs are not sufficient evidence for ML.
They do not carry effective-dated security identity or versioned raw daily bars.
M0.8 will determine whether those two pillars can be reconstructed from official
sources for the 4,846-row buyback cohort before any bulk backfill or model work.

This milestone has two independent decisions:

1. **research reconstruction feasibility** — can official responses identify the
   security that traded on each relevant date and supply reproducible raw stock
   and benchmark OHLCV observations?;
2. **production-use feasibility** — does the project have a data agreement that
   permits the intended commercial app, derived signals and user delivery?

A technical pass cannot satisfy the production-use decision.

## Facts fixed before implementation

The buyback cohort spans 2021-06-28 through 2026-06-24 and contains 4,846 rows,
1,020 stock codes and 1,163 event dates. Its recorded T0/T+1/T+2/T+5 windows use
1,222 distinct dates. A complete official KOSPI/KOSDAQ reconstruction would need
at most 2,444 market-date requests per endpoint family. Stock daily trading,
security basic information and KOSPI/KOSDAQ index history therefore have a
conservative upper bound of 7,332 requests before retries or diagnostics. The
exact existing market/date surface is 2,421 pairs: 1,211 KOSPI and 1,210 KOSDAQ.
Its exact three-family request count is therefore 7,263. The artifact must report
both the exact count and the more conservative date-by-two-markets bound.

The official KRX OPEN API advertises KOSPI/KOSDAQ daily trading, security basic
information and index history from 2010 onward. Access requires a KRX Data
Marketplace account, an authentication key and approval for each service. The
current terms limit the OPEN API to noncommercial use, prohibit charging third
parties for its results and prohibit providing received information to third
parties. They also cap a key at 10,000 requests per day. Consequently, this API
is a candidate for an internal research feasibility probe, not an assumed
production data license.

Official references:

- KRX service list: https://openapi.krx.co.kr/contents/OPP/INFO/service/OPPINFO004.cmd
- KRX access process: https://openapi.krx.co.kr/contents/OPP/INFO/OPPINFO003.jsp
- KRX terms: https://openapi.krx.co.kr/contents/OPP/INFO/OPPINFO002.jsp
- Financial Services Commission stock-price API:
  https://www.data.go.kr/data/15094808/openapi.do
- Financial Services Commission KRX-listed-security API:
  https://www.data.go.kr/data/15094775/openapi.do
- OPEN DART corporation-code contract:
  https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DE001&apiId=AE00004

The Financial Services Commission APIs are useful as an independent official
cross-check and have automatic development approval, but their posted terms are
also noncommercial and prohibit modification. OPEN DART's corporation-code file
contains current corporation code, stock code and last-modified date; by itself
it is not proof of the corporation-to-security mapping on an earlier event date.

## Questions M0.8 must answer

### Effective-dated identity

- Does a historical KRX daily/basic response expose a stable ISIN, six-character
  short code, market and security group for the requested date?
- Can ordinary shares be separated from ETFs, ETNs, preferred shares, warrants,
  SPACs and other instruments without relying on current-day state?
- Do the KRX short code, market and name agree with the frozen buyback row on a
  stratified sample, including every excluded/anomalous row?
- What official evidence links the DART receipt/corporation to that historical
  KRX security? A current OPEN DART mapping is only corroboration. If an exact
  historical bridge is unavailable, identity remains `PARTIAL` rather than
  being inferred from matching names.

### Raw daily outcomes

- Do official stock responses contain requested date, raw open/high/low/close,
  volume, value, listed shares, market, short code and ISIN, with unambiguous
  units and pagination completeness?
- Do official index responses cover the KOSPI/KOSDAQ benchmark sessions needed
  by the same rows?
- Can exact response bytes be retained locally with capture time, request
  boundary, response metadata and SHA-256 without overwriting an earlier
  version?
- Does a repeated retrieval either reproduce the same bytes or create a second
  version with an explicit byte-level and semantic diff?
- Which existing adjusted-Naver values differ from official raw values? Such a
  difference is classified, not overwritten. Corporate-action crossings are
  quarantined until a separately sourced adjustment/action policy exists.

### Production rights and operations

- Which contract permits commercial use, derived predictions and delivery to
  app users without exposing or redistributing restricted raw data?
- What attribution, retention, audit and termination obligations apply?
- What request limits, historical coverage, revision policy, service level and
  expected recurring cost apply at production scale?

If those rights cannot be evidenced in writing, the production gate is
`NO_GO_LICENSE` even if the research probe succeeds.

## Planned implementation after plan approval

### 1. Source-contract registry

Add a small source registry that records provider, endpoint family, official
documentation URL, terms URL, advertised coverage, authentication mechanism,
request limit, license class, commercial-use status and the UTC time at which
the contract was observed. Contract facts that cannot be established are
`unknown`; they are never guessed.

Secrets are accepted only through environment variables. The six core KRX
services—KOSPI/KOSDAQ stock daily, security basic and index daily—share a KRX
`AUTH_KEY` but require separate service approvals. The optional Financial
Services Commission cross-check uses a data.go.kr service key. The optional
receipt bridge uses a separate OPEN DART key and approval. Credential and
approval status is recorded separately for every provider and service.
Implementation environment names are `KRX_OPEN_API_AUTH_KEY`,
`DATA_GO_KR_SERVICE_KEY` and the repository's existing `DART_API_KEY`.

Some data.go.kr and OPEN DART contracts require authentication in a transient
wire-query parameter. Such values may exist only inside the in-memory request
sent to the provider. They must never enter a persisted or displayed URL, log,
exception, hash, fixture, manifest, artifact, stdout, chat or tool output.
Sanitized request identity includes endpoint, method and nonsecret parameters.

### 2. Immutable response envelope

Create a provider-neutral envelope for each response:

- provider and endpoint contract version;
- sanitized request identity and request SHA-256;
- retrieval time in UTC and intended Korean market date;
- status, content type, selected nonsecret response headers and raw byte count;
- raw-response SHA-256 and parser version;
- license/redistribution classification and retention/termination deadline;
- a create-only local blob reference.

Restricted raw bytes remain in a gitignored local evidence directory with
user-only filesystem permissions. The
committed feasibility artifact contains hashes, schemas, counts and diffs only.
No raw provider payload is committed until its redistribution right is clear.
Offline replay must reproduce every parser and reconciliation result from the
captured local bytes with network access disabled. If any response body or
header echoes a known credential, the capture is rejected and nothing from that
response is persisted; immutable provider bytes are never silently redacted and
then described as raw. Retention automatically expires or disables evidence as
required by the observed provider agreement.

Authenticated response bodies and field values, including provider error
payloads, must never appear in stdout, logs, exceptions, chat or tool output.
The capture path writes bytes only to the restricted local evidence store;
parsers and CLIs may emit allowed hashes, counts and categorical status/mismatch
codes. This applies to successful, provider-error and parser-error paths.

The exact public documentation and terms bytes used for the decision are also
captured locally with URL, retrieval time, effective time when stated, content
hash and byte count. Only their hashes and nonrestricted contract facts enter
the committed artifact.

### 3. Precommitted authenticated canary probe

The canary is frozen before authenticated retrieval in
`docs/history/M0.8-canary-v1.json`. Its selection hash is
`aa89e2580c81eb445ff1cbe068cfc6a3216a1c2533f6eb210a28062dbc0e4716`.
The canonical full-definition hash is
`ac94f3b62045823e759389bac641199571c4c034e9a823a5fce2dfb45df2f3f6`;
it covers selection rules, source pins, selected rows, all market/date pairs,
the two structured second-version pairs and request caps. Implementations verify
both hashes before any authenticated request.
It contains 141 unique receipts: all 46 M0.7-excluded buybacks, all 11 exact
15:30 filings, 24 admitted after-close filings (two per market/year), 12 admitted
rows without filing time (one per market/year), and 48 admitted pre-close rows
(four per market/year). Seeded ranks and all receipt/date/market choices are in
the pinned file.

Those rows cover 391 market/date pairs when event date and recorded
T0/T+1/T+2/T+5 dates are combined. The six approved KRX services therefore
require 1,173 primary requests. The precommitted second versions are the oldest
pair, KOSPI 2021-07-29, and newest pair, KOSPI 2026-07-01, adding six requests.
The hard KRX ceiling is 1,800 calls: 1,179 primary/version calls, at most 360
diagnostic calls and at most 261 retry calls. No request is sent once its budget
is exhausted. Optional
data.go.kr plus OPEN DART calls have a separate combined ceiling of 600.

The probe is fail-closed. Without all six core KRX approvals it emits per-service
authentication blockers and performs no pseudo-validation from pykrx or current
CSV values. The offline machinery may be implemented and tested, but M0.8 then
becomes `BLOCKED` pending an authenticated empirical run; `AUTH_REQUIRED` cannot
be accepted as `VERIFIED`. Missing optional data.go.kr access is reported without
blocking the core result. Missing OPEN DART access prevents the historical
receipt bridge from passing and therefore yields at best
`PARTIAL_IDENTITY_BRIDGE` after the KRX probe passes.

For each precommitted market/date pair, capture the applicable KRX stock daily,
security basic and broad-market index response. The KOSPI/KOSDAQ benchmark must
be selected by a stable provider index code; an index name is diagnostic only.
Cross-check a precommitted subset against the official Financial Services
Commission API without treating agreement as a substitute for KRX provenance.

Unexpected discrepancies may open a separate diagnostic set of at most 24
receipts and 120 new market/date pairs. Selection is deterministic by mismatch
code and then seeded receipt hash. Diagnostic results can add blockers or
downgrade the primary result; they can never clear a blocker or promote it.
Unprobed rows remain untested.

### 4. Strict reconciliation

The reconciler must fail or quarantine on:

- provider error payloads, truncation or incomplete pagination;
- requested/returned date mismatch;
- absent, duplicate or ambiguous short-code rows;
- short-code/ISIN/market/security-group inconsistency;
- unsupported instrument type;
- nonnumeric, nonfinite or nonpositive required prices;
- invalid OHLC ordering or negative volume/value;
- missing benchmark session or benchmark identified only by display name;
- a DART corporation-to-security bridge supported only by current state;
- any response whose raw bytes or parser source do not match their recorded
  hashes.

Provider silence is `not_observed`, never a delisting fact. Names are diagnostic
fields and never identity join keys.

### 5. Decision artifact

Produce `artifacts/m0_8/buyback_source_feasibility_v1.json` with:

- source-contract and license findings;
- pinned canary definition, canary census and a separately labelled full-cohort
  coverage/request projection; no unprobed row is reported as observed;
- raw/envelope/parser hashes without restricted raw payloads;
- categorical mismatch codes/counts and evidence hashes; names, codes, ISINs,
  prices or other provider-returned values are omitted unless retained written
  terms explicitly allow their redistribution;
- estimated full-backfill requests, storage, run time and cost;
- independent research and production decisions;
- fixed blockers and the next bounded milestone.

Research output contains a lexically sorted blocker set plus one summary code.
Blockers are never discarded merely because a higher-precedence summary exists.
Summary precedence is:

1. `AUTH_REQUIRED` if any of the six core KRX services is not approved;
2. `NO_GO_REPRODUCIBILITY` if capture integrity, offline replay, revision
   retention or evidence/source hashes fail;
3. `NO_GO_SOURCE_SCHEMA` if required historical fields, stable benchmark code,
   pagination completeness or canary coverage fails;
4. `PARTIAL_IDENTITY_BRIDGE` if KRX identity/raw observations pass but the
   historical DART-receipt/corporation-to-security link is unproved;
5. `GO_RESEARCH_BACKFILL` only when the sorted blocker set is empty.

`GO_RESEARCH_BACKFILL` means only that the frozen 141-receipt canary supports
attempting a separately planned full backfill. It does not certify listing or
delisting intervals, the other 4,705 receipts, full-cohort completeness, or
closure of an M0.7 evidence pillar.

Production output uses this independent precedence:

- `GO_PRODUCTION_LICENSED` only when a retained, applicable written agreement
  supersedes conflicting public terms and covers commercial derived signals and
  user delivery;
- `NO_GO_LICENSE` when applicable public terms explicitly prohibit the intended
  use and no retained superseding agreement exists;
- `LICENSE_REVIEW_REQUIRED` only when the applicable or superseding terms are
  genuinely unclear and under review, rather than explicitly prohibitive.

The overall ML gate remains `NO_GO` after M0.8 regardless of a research-source
pass because M0.7's exact disclosure-version and cross-category-conflict
blockers are outside this milestone. M0.8 can establish raw-source feasibility;
it does not select an adjustment, total-return or corporate-action policy and
therefore cannot close M0.7's versioned daily-label pillar.

## Test plan

Tests use synthetic provider fixtures and locally captured canaries only. They
must cover:

- sanitized transient request identity plus log/exception handling on success,
  HTTP-error and parser-error paths, with no persisted or displayed credential;
- a credential echoed in any response body or header yields zero raw blobs,
  zero envelopes and zero conclusion inputs; provider bytes are not redacted;
- authenticated provider values never reach stdout, logs, exceptions, chat or
  tool output; capture-output regressions cover success, provider-error and
  parser-error paths and allow only hashes, counts and categorical codes;
- create-only response storage, collision handling and multi-version retention;
- offline replay with all network entry points forced to fail;
- byte tampering, parser-source tampering and contract-metadata tampering;
- error payloads, pagination truncation, duplicate codes and schema drift;
- date, ISIN, market and instrument mismatches;
- raw OHLCV validation, benchmark gaps and corporate-action quarantine;
- current-only DART mappings rejected as historical identity proof;
- stable decision codes under row and response ordering permutations;
- inability to turn `AUTH_REQUIRED` or a research pass into a production pass;
- multiple simultaneous blockers and the fixed summary precedence;
- diagnostic follow-ups that can downgrade but never promote the canary;
- protected-path and existing-destination rejection using the verified M0.7
  publication primitive rather than another writer.

No test should merely mirror implementation branches. The central integration
test must replay captured bytes offline and independently recompute the canary
census and both decisions.

- [ ] Exact official source and terms evidence is recorded with observation time.

## Explicit non-goals

- No bulk 4,846-row source backfill.
- No replacement or repair of frozen event-study rows.
- No adjusted-price policy, total-return policy or corporate-action backfill.
- No disclosure-document recovery or cross-category canonicalization.
- No feature creation, model training, transformer work or M3.2 work.
- No production claim based on free/noncommercial API access.
