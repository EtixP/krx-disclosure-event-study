# M2.1 — Versioned experiment specification

## Objective

Freeze a complete prospective research definition before its forward events are
observed. M2.1 defines and preserves experiment configuration; it does not log
event decisions, attach outcomes, evaluate a strategy, or place an order.

## Specification boundary

`ExperimentSpecification` is a strict, deeply frozen `m2.1-v1` model. It records:

- stable experiment ID, integer version, name, and objective;
- UTC creation time, historical data cutoff, and forward-test start;
- canonical event types, markets, statuses, lineage states, and normalization
  version;
- named decision-time-only features with source and source version;
- explicit broad-market mappings, source/version, exact-date alignment, return
  type, and fail-on-missing policy;
- typed eligibility predicates and exclusions;
- versioned entry and exit rule IDs with immutable scalar parameters;
- commission, VAT, slippage, tax-policy, currency, and model versions; and
- evaluation end, sample minima, primary metric, success criteria, failure
  criteria, fixed all-success/any-failure/failure-over-success match semantics,
  and an explicit inconclusive policy.

Set-like fields require unique sorted order so semantically equivalent input
cannot acquire different hashes merely through ordering. Values are finite,
predicates have compatible operands, every event market has a benchmark, the
historical cutoff cannot follow creation, creation strictly precedes the forward
start, and evaluation ends later than that start. All timestamps use UTC to
avoid offset-dependent registry order.

`canonical_json()` emits compact, key-sorted UTF-8 JSON with no non-finite
encoding. `sha256()` hashes those exact bytes. The hash covers identity,
chronology, methodology, all rules, and the predecessor link.

## Append-only lifecycle

The registry stores two types of immutable fact:

```text
experiment_specifications
    canonical definition + SHA-256 + registration chronology

experiment_activations
    experiment/version + the same SHA-256 + activation timestamp
```

SQLite triggers reject updates and deletes from both tables. `init_db()` enables
and verifies SQLite foreign-key enforcement before schema use, so an activation
cannot exist without its referenced specification. Registration is idempotent
for an identical existing version throughout its lifecycle. Registration and
activation timestamps come from the registry's UTC clock rather than public
method arguments, preventing API-level backdating. First registration and
activation must occur no later than the forward-test start; repeated activation
returns the original immutable activation fact. Registration also reparses
canonical JSON, so an unvalidated `model_copy` cannot bypass schema invariants
before storage.

Evaluation semantics are part of the canonical bytes: all success criteria must
match, any failure criterion is sufficient, failure wins if both sides match,
and a match on neither side produces an explicit inconclusive result. The same
semantic metric/operator/threshold condition cannot appear in both sets.

The initial definition is version 1 with no predecessor. After activation, a
change uses `ExperimentRegistry.revise(...)`, which creates version `n + 1` and
sets `supersedes_sha256` to version `n`'s exact hash. Only the latest activated
version may be revised; creation and forward start must increase. Registering a
skipped version, an unactivated predecessor, or a false predecessor hash fails.
The new version remains unactivated until a separate activation fact is added.

Every load revalidates the canonical JSON, stored hash, redundant chronology
columns, activation hash/time, contiguous versions, predecessor hash chain, and
increasing creation/start/activation chronology. A row that is internally
well-formed and rehashed still fails if its chain contradicts the predecessor.

## Deterministic definition replay

`active_at(experiment_id, assessed_at)` uses an explicit UTC timestamp. It first
requires that activation and the version's forward start were knowable by that
time, then selects the highest started version. Once a successor starts it
permanently supersedes the predecessor; if that successor's evaluation window
has ended, the result is no active version rather than resurrection of the old
definition. `replay(...)` applies this rule to a sequence of timestamps.

This is deterministic *definition selection*, not outcome replay. M2.2 will
record considered events and frozen decisions; M2.3 will attach outcomes under
the selected specification. M2.1 deliberately stores neither.

## Independent verification failure (2026-09-10)

Three lifecycle/specification gaps prevented acceptance.

First, `init_db()` does not enable SQLite foreign-key enforcement: the verifier
observed `PRAGMA foreign_keys = 0`. SQLite accepted an activation referencing a
nonexistent experiment/version. When a matching specification with the same
hash was registered later, the registry joined that old row, reported the
specification as activated, and selected it at its forward start even though
`ExperimentRegistry.activate()` had never run. The declared foreign key must be
enabled and covered by an orphan-activation regression.

Second, identical registration is only idempotent before the forward start.
`_register_at()` applies the current-time cutoff before checking whether the
same immutable version already exists, so a restart/retry after the start raises
instead of returning the original fact. A no-op retry must remain idempotent
without permitting a changed or new definition to register late.

Third, the same criterion can be placed in both `success_criteria` and
`failure_criteria`. No conjunction/disjunction or simultaneous-match policy is
recorded, so a later outcome evaluator could choose classification semantics
after prospective data exist. M2.1 must freeze non-ambiguous evaluation
semantics before M2.2 begins.

The valid path otherwise held. Targeted and full suites passed `19/19` and
`343/343`; canonical hashes, ordinary version/replay behavior, SQL update/delete
triggers, Black, compilation, and diff checks passed. M0.4, M0.5, and M1.1
regenerated byte-for-byte at their verified hashes. M2.1 returns to `IN
PROGRESS`; M2.2 remains `NOT STARTED`.

## Builder correction after verification failure (2026-09-10)

`init_db()` now executes and verifies `PRAGMA foreign_keys = ON` before schema
initialization. A regression performs the verifier's raw orphan insertion,
confirms SQLite rejects it, registers the would-be matching specification, and
confirms that it has no activation and is not active at its forward start.

`_register_at()` now canonicalizes and validates the proposed specification,
then resolves the immutable identity before applying current-time bounds that
govern creation of a new fact. A byte-identical retry therefore returns the
original registration after the forward start. Changed content under that
identity still raises the immutability error, while a new late definition still
fails prospective chronology.

`EvaluationPlan` now places its aggregation and conflict choices in canonical
JSON: success uses `all`, failure uses `any`, a simultaneous match resolves to
failure, and neither side remains `report_inconclusive`. Each choice is a strict
literal, so changing it requires a future schema/version decision rather than a
post-observation evaluator choice. Semantically identical conditions across the
success and failure sets are rejected even when their display names differ.

The targeted suite passed `22/22`; the repository-local full suite passed
`346/346`. Black, compilation, and `git diff --check` passed. M0.4, M0.5, and
M1.1 regenerated byte-for-byte at `1acf9366…`, `3677a4c2…`, and `33ff2517…`.
No research output changed, no production experiment was created, and M2.2 was
not started. M2.1 is `AWAITING VERIFICATION`.

## Independent re-verification (2026-09-10)

The verifier replayed the three original failures without relying only on the
new regressions. Fresh and reopened `init_db()` connections reported
`PRAGMA foreign_keys = 1`; an orphan activation failed, and later registration
did not inherit an activation. A read-only `foreign_key_check` of the existing
repository database found zero violations.

After closing and reopening the registry beyond the forward start, an identical
specification returned its original registration. Changed content under the
same experiment/version still failed immutability, and a new late experiment
still failed prospective chronology. Canonical evaluation JSON retained the
fixed all-success, any-failure, failure-over-success, and inconclusive policies
through round-trip validation; an identical condition renamed across outcome
sets was rejected.

Targeted and full suites passed `22/22` and `346/346`; Black, compilation, and
diff checks passed. M0.4, M0.5, and M1.1 regenerated byte-for-byte at
`1acf9366…`, `3677a4c2…`, and `33ff2517…`. Normal version/replay behavior,
research outputs, and verified upstream artifacts remained unchanged. M2.1 is
`VERIFIED`; M2.2 was not started.
