# M1.2 — Incremental live DART watcher

## Objective

Add a small, inspectable live ingestion loop that detects DART filings,
persists source material before interpretation, normalizes through the verified
M1.1 event core, and hands immutable event snapshots to downstream consumers.
The milestone does not decide significance, generate signals, or place orders.

## Provider constraints

The official
[OPEN DART disclosure-search guide](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001)
documents `list.json`, a maximum `page_count` of 100, update-inclusive
`last_reprt_at=N`, response pagination, status `020` for request-limit
exhaustion, and a general rather than guaranteed 20,000-request threshold. The
watcher therefore requests 100 records per page and ascending receipt-date
order, refuses non-finite polling intervals and values
below 60 seconds, and never hides status `020`. DART exposes no receipt-number
tie-breaker, so traversal does not assume monotonic receipt numbers; durable
receipt-key idempotency makes repeated observations safe. Other programs using
the same API key and unusually large multi-page days still share the provider
quota; the journal makes any resulting failure explicit instead of claiming a
quota guarantee it cannot provide.

The current date is derived in `Asia/Seoul`, while processing timestamps are
stored as timezone-aware UTC values. The OPEN DART list supplies only the
source receipt date. An invalid or missing `rcept_dt` now fails rather than
being replaced with the local current time.

## Durable state transitions

M1.2 adds seven append-oriented or state-journal tables:

1. `live_poll_runs` records successful, failed, and interrupted cycles.
2. `dart_disclosure_observations` retains every distinct raw list-record
   payload and observation time without overwriting the first-seen disclosure.
3. `dart_relationship_captures` stores exact viewer response bytes, their hash,
   and the parsed M1.1 relation object; multiple response vintages may coexist.
4. `live_receipt_processing` journals queued, processing, failed, and processed
   receipt work.
5. `canonical_event_snapshots` freezes the event handed downstream for each
   trigger receipt.
6. `economic_event_aliases` retains provisional receipt-derived event IDs when
   later authoritative lineage reveals an older primary.
7. `event_deliveries` journals per-consumer intent, attempts, failures, and
   acknowledgement.

The write order is an invariant:

```text
raw list page commit
    ↓
raw relationship bytes commit (when needed)
    ↓
M1.1 normalize_disclosures
    ↓
immutable canonical snapshot commit
    ↓
delivery intent commit
    ↓
consumer call
    ↓
delivery acknowledgement
```

Hashes on stored relationship bytes and canonical JSON are verified again on
read. Parsed relationship fields are also re-derived from the exact viewer
bytes and compared on both save and reload, preventing a validly structured but
unevidenced lineage object from entering normalization. A changed DART `rm`
observation is retained as another raw vintage but does not overwrite
decision-time raw input or requeue an acknowledged receipt.

## Idempotency and recovery contract

A receipt is queued only once. A successful `(consumer_name, trigger_receipt)`
delivery is skipped on later polls and replays. Failed consumers retry with the
same SHA-256 delivery ID, while already successful sibling consumers do not run
again. A new process marks abandoned poll, processing, and delivery states as
interrupted and makes the latter two retryable.

No local journal can guarantee exactly-once effects across an arbitrary
consumer boundary: the process can die after a consumer performs a side effect
but before SQLite records acknowledgement. M1.2 therefore provides at-least-once
recovery for that narrow ambiguity and requires consumers to use `delivery_id`
as their idempotency key. It does not claim distributed exactly-once delivery.

The CLI is designed for one active writer per SQLite database. Multi-process
leader election is not part of this milestone.

## One event path and replay

`LiveDartWatcher` calls the verified `normalize_disclosures` function directly.
It does not contain a live-only classifier. For update/cancellation/completion
filings, it recursively loads available source rows and persisted authoritative
relations; missing source rows remain `partial` under M1.1 rather than being
guessed.

`replay` accepts explicit historical receipt numbers already present in the
existing `disclosures` table. It creates or reuses the same immutable snapshot
and calls the same delivery function as live processing. With no explicit
receipt list, it replays existing snapshots only, avoiding an accidental scan
of the 1.2-million-row historical corpus.

## Remaining limitations and handoff invariants

- This is polling, not push delivery. A filing is observed no earlier than the
  next successful cycle.
- Historical relationship pages are not bulk-backfilled. M1.2 persists them as
  newly processed update components require them.
- Full disclosure-document ZIPs are still fetched by downstream parsing paths,
  not by the watcher itself; the raw event here is the complete list record plus
  any relationship evidence used for normalization.
- The built-in `canonical-event-log-v1` consumer only logs event metadata.
  M1.3 may add significance interpretation as a consumer but must not fork the
  ingestion or normalization core.
- No strategy, signal, risk decision, broker API, order, or execution behavior
  belongs to this watcher.

M1.2 is `AWAITING VERIFICATION`. M1.3 was not started.

## Independent verification result

Independent verification on 2026-09-07 returned M1.2 to `IN PROGRESS`.

The core durable workflow held. A fresh temporary-database run reproduced two
pages and 158 KOSPI records, with 158 raw observations, 20 immutable snapshots,
zero failures, and 138 queued receipts. A second SQLite connection observed the
raw row, snapshot, and `delivering` intent before consumer execution. A malformed
two-record page rolled back all page writes. Restart/retry, replay, stable
delivery IDs, successful-consumer isolation, and the no-trading dependency
boundary also passed.

Two correctness gaps remain. First, `WatcherPolicy` compares the polling
interval only with `< 60`; IEEE `NaN` makes that comparison false and is
accepted. The run-loop then computes a zero-second wait, defeating the claimed
source-safety floor. Positive infinity is also accepted. All user-facing timing
values must be finite before bounds are applied.

Second, the saved parsed relation is not cryptographically or semantically
bound to the captured viewer bytes. Changing only `relations_json` to replace
the original receipt with another valid receipt survives `get_latest_relationship`
because the embedded hash still matches the unchanged raw HTML. Likewise,
`save_relationship_capture` accepts a relation/raw pair whose receipt sets
disagree as long as the relation cites the bytes' SHA-256. Recovery can thus
normalize invented lineage under an evidence hash for bytes that do not contain
it. Reparse-and-compare on save/read, or an equivalently strong binding, is
required.

The official API offers ascending sorting by receipt date, not an explicit
receipt-number tie-breaker. The fresh 158-row response was not monotonic by
`rcept_no`. Claims that traversal is in stable ascending receipt order must
therefore be removed or backed by an enforced and safe ordering design.

Focused tests passed `46/46`, the full suite passed `236/236`, and scoped Black,
compile, and diff checks passed. M1.1 and M0.5 regenerated byte-for-byte; all
verified M0.1–M1.1 hashes and research results remained unchanged. M1.3 was not
started.

## Builder correction after verification failure

On 2026-09-07, poll-policy construction was made finite before bounds are
evaluated. `NaN`, positive infinity, and negative infinity now fail explicitly;
the 60-second minimum remains unchanged.

Relationship capture now has one deterministic byte-derived interpretation.
Fresh retrieval parses the exact `response.content` bytes, and
`LiveEventStore` independently re-parses those bytes with the stored receipt,
source URL, and computed hash. Save rejects an inconsistent relation/raw pair;
reload rejects altered `relations_json` even when both the raw bytes and their
SHA-256 are unchanged. The original byte-hash corruption check remains in
place.

The ordering contract was corrected rather than inventing a provider
capability. The client requests `sort=date&sort_mth=asc`, preserves the
provider's within-date order, and makes no receipt-number monotonicity claim.
Repeated polling remains safe through raw-observation and receipt idempotency.

The focused suite passed `51/51` and the full suite passed `241/241`. Scoped
Black, compilation, and `git diff --check` passed. A fresh temporary-database
smoke test reproduced 158 records, 20 snapshots, zero failures, and 138 queued
receipts. M1.1 and M0.5 regenerated byte-for-byte at `33ff2517…` and
`3677a4c2…`; all verified M0.1–M1.1 artifact hashes remained unchanged. M1.2 is
`AWAITING VERIFICATION`; M1.3 was not started.

## Independent re-verification

On 2026-09-07, independent verification replayed the two prior evidence attacks.
An inconsistent parsed relation/raw-byte pair is rejected without a database
write, and altering only valid `relations_json` while retaining the original
HTML and hash is rejected on reload. `NaN`, both infinities, strings, booleans,
and values below 60 seconds all fail before polling.

The official API guide confirms `sort=date`, `sort_mth=asc`, and a maximum
100-row page, but offers no receipt-number tie-breaker. A fresh two-page response
again contained 158 same-date KOSPI records in non-monotonic receipt-number
order; all were persisted safely, 20 normalized and delivered successfully,
none failed, and 138 remained queued.

Focused and full suites passed `51/51` and `241/241`. Page atomicity, external
commit visibility, recovery, replay, delivery idempotency/isolation, and the
no-trading boundary held. Scoped Black, compilation, and diff checks passed.
M1.1 and M0.5 regenerated byte-for-byte at `33ff2517…` and `3677a4c2…`, with all
earlier verified hashes unchanged. M1.2 is `VERIFIED`; M1.3 remains `NOT
STARTED`.
