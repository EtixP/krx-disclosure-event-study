# M2.2 — Forward event ledger

## Objective

Record every canonical event delivered while one or more frozen experiments are
active, including events that fail scope, feature, eligibility, or exclusion
rules. The record must exist before any prospective outcome is attached. M2.2
does not calculate outcomes, emit orders, or authorize execution.

## Decision-time boundary

The live watcher hands the ledger the same immutable M1.2 `EventEnvelope` used
by alerts. Its canonical snapshot `normalized_at` becomes the UTC decision
cutoff. M1.3 significance and M1.4 historical context are built at exactly that
cutoff through `ResearchAlertBuilder`; the event, significance result, context
result or structured unavailability, and extracted feature values are embedded
in an `m2.2-v1` `DecisionInputSnapshot`.

Each feature snapshot records its frozen M2.1 name, source, requested and actual
source versions, source SHA-256, field path, value type, missing policy, status,
and value. Deserialization re-derives event identity, delivery identity,
significance, source hashes, field resolution, type handling, and feature
values. Timestamps serialize as timezone-aware ISO strings. Missing, unavailable,
wrong-version, wrong-type, and non-finite inputs never become zero.

An event whose trigger source predates the forward start is retained with
`PRE_FORWARD_SOURCE` rather than silently dropped. An event snapshot containing
a source later than the decision cutoff fails before a decision can be written.
Historical replay is not wired to the forward-decision consumer.

## Complete active-experiment coverage

`ExperimentRegistry.active_experiments_at()` returns all active definitions in
stable experiment-ID order. `ForwardDecisionConsumer` builds one shared source
assessment and then one decision per active experiment. All decisions for the
event are validated before `record_many()` inserts them in one SQLite
transaction, preventing a partial active-experiment batch.

The deterministic evaluator applies:

- frozen event type, market, status, lineage, and normalization scope;
- every versioned feature definition and its missing policy;
- every eligibility predicate; and
- every exclusion predicate.

Incompatible predicate types fail closed. An `eligible` record has no rejection
reasons; every `rejected` record contains sorted structured reasons with a code,
rule/feature identity where applicable, and detail. This is experiment
eligibility only and fixes `authorizes_execution=False`.

## Append-only persistence and provenance

Each `ForwardDecision` embeds the exact M2.1 specification and hashes both that
definition and the complete decision-input snapshot. Its deterministic ID is:

```text
SHA256("m2.2:" + experiment_sha256 + ":" + decision_input_sha256)
```

The SQLite row redundantly stores decision identity, experiment/version/hash,
activation timestamp, trigger/event hash, input hash, disposition, reasons,
decision hash, decision time, and first recorded time. Every read reparses the
canonical JSON and reconciles all redundant columns.

Composite foreign keys require the exact experiment specification, its exact
pre-existing activation fact, and the exact M1.2 canonical event snapshot. A
decision cannot be preinserted before activation and later attach to it. Update
and delete triggers make decision rows append-only. Re-recording identical bytes
returns the first record without changing `recorded_at`; conflicting bytes under
the same experiment-version/trigger identity fail.

## Live integration and scope

Both live watch entry points install `ForwardDecisionConsumer` alongside their
existing output consumer. When no experiment is active it performs no feature
or historical-context work and writes no decision. No production experiment was
registered or activated by this milestone.

The decision table contains no outcome, return, PnL, fill, order, or execution
columns. M2.3 must attach future outcomes in a separate layer without updating
these rows.

## Second builder correction — complete non-finite coverage

The correction keeps the boundary inside M2.2. M1.2's event schema, canonical
snapshot storage, hashes, and delivery behavior are unchanged. At the decision
boundary, the exact M1.2 canonical event JSON and SHA-256 are copied into the
input snapshot. M1.2's JSON projection represents a non-finite normalized float
as `null`, so M2.2 additionally records a sorted tuple containing the path and
kind (`nan`, `positive_infinity`, or `negative_infinity`) observed in the source
event. The tuple is ordinary JSON data and is covered by the decision-input and
decision hashes.

Strict input validation parses the retained event JSON while rejecting
non-standard JSON constants, requires every recorded path to point to a
canonical `null`, restores the typed value only in memory, and re-derives the
canonical JSON/hash and complete path/kind tuple. It then re-derives delivery
identity, source chronology, significance, historical-context identity, and all
feature snapshots. SQLite reference validation still requires the retained
canonical JSON/hash to match the immutable M1.2 snapshot exactly. The outer
decision serializer retains `allow_nan=False`; neither `NaN` nor `Infinity`
appears as a JSON number. Numeric predicates now use the same finite-number
test as feature extraction and therefore fail closed.

Parametrized full-path regressions cover `NaN`, positive infinity, and negative
infinity. In each case, the configured numeric feature is `type_mismatch`, the
active experiment receives exactly one rejected row with
`FEATURE_TYPE_MISMATCH` and `ELIGIBILITY_INPUT_MISSING`, and the decision
survives strict JSON parsing, SQLite persistence, reload, and source-reference
reconciliation. The arbitrary-precision `10**1000` case continues to record an
eligible decision exactly.

## Third builder correction — source-bound canonical identity

The prior sidecar could not prove what M1.2 had stored because Pydantic's JSON
projection collapsed a genuine `None`, `NaN`, positive infinity, and negative
infinity to the same `null`. The correction moves that distinction into the
canonical source representation. A finite or genuine-null event retains its
existing canonical bytes. Only an event containing a non-finite value is stored
inside a strict-JSON `m1.2-non-finite-v1` envelope containing the ordinary event
projection and sorted path/kind metadata. The complete envelope is hashed and
feeds the M1.2 delivery ID, so all four source states are distinct.

`event_from_canonical_snapshot()` rejects non-standard JSON constants, validates
the extended envelope and every path, restores the source floats in memory, and
requires re-canonicalization to reproduce the exact input bytes. M1.2 snapshot
reload now uses that one decoder. Consequently, first delivery and post-restart
delivery reconstruct the same event and produce the same M2.2 input hash,
decision ID, feature status, reasons, and canonical decision bytes. M2.2 embeds
the exact upstream JSON/hash and no longer has a separately forgeable metadata
field. An envelope containing `NaN` cannot reconcile against a stored genuine
null because both its event hash and delivery ID differ.

Predicate comparison was corrected independently. If either equality or
membership operand has a numeric Python type, both operands must satisfy the
finite-number boundary before comparison. Non-finite values therefore return
the structured invalid-predicate path for `eq`, `ne`, `in`, and `not_in`, while
the existing ordered-comparison checks remain in force. This prevents `ne` from
turning IEEE exceptional values into eligible observations.

Finally, `kdtb.event_identity` no longer imports `EconomicEvent` while the
module is initializing. The type is imported only for static checking and
inside snapshot decoding, so direct import works in a fresh interpreter without
depending on which schema module was imported first.

Direct regressions cover all three non-finite forms across all four equality and

import. Targeted M2.2, combined M2.1/M2.2, focused M1.2, and full suites passed
`27/27`, `49/49`, `19/19`, and `373/373`. Black, compilation, CLI help,

- `{True: NaN}` projects its key as `"true"` but records metadata path `"True"`,

## Fourth builder correction — lossless persistence gate

The correction deliberately rejects unsupported lossy source shapes instead of
adding another partial key encoding. `EconomicEvent` now validates the declared
`dict[str, Any]` contract recursively: every mapping nested anywhere within
`normalized_fields` must have string keys. The exact boolean-key and
integer/string-collision inputs are therefore no longer schema-valid.

As defense in depth, `canonical_event_snapshot()` builds the same ordinary or
non-finite extended payload, then decodes it through the shared loader and
compares the original and restored Python-mode event values. The comparison
requires identical concrete types, recursively matches mapping keys without
Python's boolean/integer equivalence, preserves list-versus-tuple identity, and
treats `NaN` as equal only to `NaN` for this round-trip test.

If JSON key normalization, key collision, container conversion, or another
serialization effect changes the source, canonicalization raises
`canonical event snapshot cannot losslessly round-trip source values`. No
canonical bytes/hash are returned to the caller as an accepted snapshot. The
existing extended envelope still losslessly supports string-keyed `NaN`,
positive infinity, and negative infinity.

`LiveEventStore.save_snapshot()` additionally calls the canonical decoder on
the completed payload before entering `with self.conn`. This is intentionally
redundant with the serializer's invariant: it makes the storage contract
explicit and prevents future divergence between generation and loading from
committing an unreadable immutable row.

Parametrized regressions reproduce `{True: NaN}` and
`{1: NaN, "1": +inf}` inside a nested mapping. Both fail normal schema
validation. Additional defense-in-depth cases bypass validation with
`model_copy(update=...)` while an active experiment has a separate valid
`score=0.75` feature; both fail at the canonical boundary and leave zero
`canonical_event_snapshots` and zero forward decisions. Supported non-finite
store/reload/retry behavior, four-way null identity, raw predicate safety,
source substitution rejection, fresh import, and `10**1000` remain covered.

## Fifth builder correction — conflict-replacement immutability

SQLite's `REPLACE` conflict algorithm deletes conflicting rows before inserting
the replacement. SQLite invokes delete triggers for that implicit deletion only
when `recursive_triggers` is enabled, so the existing immutable-delete trigger
was insufficient while `init_db()` retained the default disabled setting.

`init_db()` now sets `PRAGMA recursive_triggers=ON` and reads the pragma back,
failing connection initialization if SQLite did not accept it. This mirrors the
existing foreign-key enforcement pattern and applies to every repository-
managed production connection. With the setting active,
`forward_event_decisions_no_delete` sees the implicit deletion and aborts the
whole replacement before any row changes. It protects conflicts selected by
the table's primary key or either current unique constraint without duplicating
those identities in another trigger.

The direct regression first records a valid eligible decision, then executes
the verifier-shaped `INSERT OR REPLACE ... SELECT` while changing only
`recorded_at` by 30 days. It asserts that recursive triggers are enabled, the
statement raises the immutable-decision integrity error, and ledger reload
returns the complete original `StoredForwardDecision`, including its first-
recorded timestamp. The existing direct update/delete assertions and later
database reopen remain in the same test.
