# M1.3 — Event significance engine

## Objective

Answer why a canonical disclosure matters in measurable economic terms without
turning magnitude into a return forecast, signal, or trading recommendation.
The same deterministic function must accept both live and replayed M1.1 events.

## Supported measurement boundary

The repository currently has a deterministic, validated extraction path for
supply-contract value, prior-year revenue, and their ratio. M1.3 therefore
supports only `contract_to_revenue_ratio`. It does not assign placeholder scores
to buybacks, dilution events, timing, or liquidity because reliable normalized
inputs for those features do not yet exist.

For a supply-contract event, the engine:

1. uses a positive, finite reported normalized ratio when present;
2. checks it against positive integer contract/revenue components when both are
   present;
3. rejects a relative discrepancy above 5%, matching the existing deterministic
   extraction tolerance;
4. otherwise derives the ratio from the two components; and
5. reports missing inputs without converting them to zero.

A read-only check of the local extraction database found 3,425
`deterministic_supply_contract_v1` rows with `validation_status=ok` and complete
ratio components. All passed this tolerance; the largest relative discrepancy
was approximately 3.169%, caused by reported-ratio rounding.

## Comparable-population definition

Percentiles are optional because M1.3 does not invent or silently query a
historical dataset. A caller may supply a `ComparableSignificanceDataset` with
an explicit `dataset_id`. Each observation records canonical event ID, event
type, market, issuer, source receipt, decision-time `known_at`, metric, and
value.

For a current measurement, the broad comparison contains exactly:

- the same metric, canonical event type, and market;
- a different canonical event ID;
- a source receipt strictly lower than the current event's latest source
  receipt;
- an observation known no later than `assessed_at`; and
- one latest eligible observation per canonical event.

The issuer-history population further requires the same `corp_code`. The engine
sorts retained observations deterministically and records every comparable
event ID, dataset ID, order-independent full-dataset SHA-256, receipt/time
cutoff, and sample size in its output. Reusing a label for changed content is
therefore visible.

The empirical rank uses midranks:

```text
100 × (count(value < current) + 0.5 × count(value = current)) / n
```

The default broad minimum is 20 canonical events; the same-issuer minimum is
five. Below those floors, sample size remains visible but percentile is `None`
with `insufficient_population` status. With no dataset, status is
`no_comparable_dataset`.

## Decision-time and output contract

`assessed_at` and observation `known_at` must be timezone-aware and cannot
predate the latest of the canonical update timestamp and every provenance
receipt timestamp. Source-naive DART timestamps are interpreted as Korean local
wall-clock time. A date-only source represented at 00:00 therefore carries only
date-level precision; callers must not claim finer historical availability
without a recovered filing time. Receipt and availability cutoffs are applied
by the engine itself, so input ordering or later revisions cannot change
replayed results by accident. Historical and live callers serialize the same
`EconomicEvent` and invoke the same `assess` method; no mode-specific feature
path exists.

`EventSignificance` records measurement derivation, source field names,
components when known, canonical event/lineage status, missing inputs,
population definitions, limitations, and human-readable explanation lines. It
structurally fixes `is_trade_recommendation` to `False` and
`trading_recommendation` to `None`. Percentile is event magnitude only—not
expected return, statistical evidence of an edge, or a reason to trade.

## Remaining limitations and handoff invariants

- M1.3 does not fetch documents or fundamentals and does not claim fields that
  are absent from the canonical event.
- It defines and evaluates comparable populations but does not provide the
  durable historical query/dataset service planned for M1.4.
- It does not compute historical returns, confidence intervals, or outcome
  context; that remains M1.4 and must use verified Phase 0 machinery.
- It does not format alerts, register experiments, generate signals, manage
  risk, or place orders.
- New event-type measurements require reliable normalized inputs, explicit
  units/derivation, missing-data behavior, chronology tests, and their own
  comparable-population semantics.

M1.3 is `AWAITING VERIFICATION`. M1.4 was not started.

## Independent verification result

Independent verification on 2026-09-08 returned M1.3 to `IN PROGRESS` after
two adversarial failures.

First, the component-consistency calculation divides relative error by
`max(abs(computed_ratio), 1e-12)`. Because both components are required to be
strictly positive, no zero-denominator guard is needed. With contract value
`1`, prior revenue `10^15`, and reported ratio `5e-14`, the engine accepted the
measurement even though the derived ratio is `1e-15` and the true relative
error is 4,900%. This contradicts the documented 5% rule.

Second, current-event chronology is checked only against the calendar date
encoded in the latest receipt number. A replay assessment at 12:00 KST accepted
normalized fields from a same-date correction whose provenance timestamp and
`latest_update_timestamp` were 15:00 KST. When canonical source timestamps are
available, assessment must not precede them; date-only source records still
need an explicit, documented availability treatment.

The local database's 3,425 complete validated deterministic extraction rows all
remain within 5%, with maximum relative discrepancy 3.169%, so no historical
headline changed. Focused and full suites passed `62/62` and `264/264`, but lack
these boundary regressions. Scoped Black, compilation, and diff checks passed.
M1.1 and M0.5 regenerated byte-for-byte at `33ff2517…` and `3677a4c2…`; all
verified upstream hashes remained unchanged. M1.4 was not started.

## Builder correction after verification failure

The component-derived ratio is always positive because both normalized
components must be positive integers. The consistency calculation now divides
by that ratio directly, with no absolute floor. The reported `5e-14` versus
derived `1e-15` adversarial case is rejected at its true 4,900% relative
difference.

The `assess` and `observe` boundaries now compare their timezone-aware decision
time with the latest of `latest_update_timestamp` and every provenance
`receipt_timestamp`. Naive source timestamps are localized to `Asia/Seoul`;
aware timestamps are converted there before comparison. A 12:00 KST decision
over a 15:00 KST source fails, while a decision exactly at 15:00 succeeds.

Focused tests passed `64/64`, and the full suite passed `266/266`. All 3,425
complete validated real extraction rows continue to satisfy the exact 5% rule,
with maximum discrepancy 3.169%. M1.1 and M0.5 regenerated byte-for-byte at
`33ff2517…` and `3677a4c2…`; all category outputs were unchanged. Scoped Black,
compilation, and diff checks passed. M1.3 is `AWAITING VERIFICATION`; M1.4 was
not started.

## Independent re-verification

Independent verification on 2026-09-08 replayed the original tiny-ratio attack
through both `assess` and `observe`. Each rejected the reported `5e-14` versus
derived `1e-15` value at its true 4,900% discrepancy, while a nearby valid
`1.04e-15` ratio remained measurable.

The prior chronology attack was expanded to a composite amended event with a
naïve Korean-local primary timestamp and an aware correction timestamp. Both
entry points rejected assessment/observation at 12:00 KST before the 15:00 KST
correction, then accepted exactly at 15:00. This confirms the maximum is taken
across the canonical update and every provenance timestamp after timezone
normalization.

Focused and full suites passed `64/64` and `266/266`. The read-only extraction
audit found all 3,425 complete validated rows within 5%, with maximum discrepancy
3.169%. Scoped Black, compilation, and diff checks passed. M1.1 and M0.5
regenerated byte-for-byte at `33ff2517…` and `3677a4c2…`; all earlier verified
hashes and research conclusions remained unchanged. M1.3 is `VERIFIED`; M1.4
remains `NOT STARTED`.
