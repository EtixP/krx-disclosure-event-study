# M3.1 — Prospective intraday market-data collection

## Objective

Capture authentic market observations after selected canonical disclosure
events without treating historical daily closes as executable intraday prices,
inventing missing rows, or weakening the event/provenance boundaries built in
M1–M2.

## Verified provider boundary

The implemented source is Korea Investment & Securities' production REST
endpoint `inquire-time-dailychartprice` (`FHKST03010230`) for dated domestic
stock minute bars. KIS's official sample documents:

- a maximum of 120 rows per call;
- explicit stock, business-date, and through-time parameters;
- historical retrieval only for data retained by KIS, at most one year;
- KRX selection with market code `J`.

Official sources:

- <https://github.com/koreainvestment/open-trading-api/tree/main/examples_llm/domestic_stock/inquire_time_dailychartprice>
- <https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_time_dailychartprice/chk_inquire_time_dailychartprice.py>

The separate `inquire-time-itemchartprice` endpoint was rejected for this
collector: KIS documents only 30 current-day rows and warns that a future-time
query can return the current price for the intervening future range. Bid/ask
REST and WebSocket capabilities exist in official samples but were not added;
the milestone can meet its acceptance criteria with one narrow, auditable bar
source.

## Design

An immutable collection target binds:

- trigger receipt and exact canonical event hash;
- economic-event ID and issuer stock code;
- DART's date-precision source date;
- the exact UTC time the raw DART list response was first retained;
- canonical normalization time;
- selected market date;
- provider and endpoint.

The target rechecks the canonical snapshot and earliest raw DART observation.
It does not claim DART supplied an exact filing time when the list API supplied
only a date.

Each KIS page follows `request → retained bytes/hash → strict parse → append-only
observations`. The store, not a caller-supplied parsed sidecar, reconstructs the
request and re-parses the retained bytes. It validates strict JSON, provider
success, exact requested date, the page cursor, KST timestamps, integer OHLCV,
OHLC consistency, and non-conflicting timestamps. Only public request fields are
stored; credentials and tokens are excluded.

Rows remain distinct provider-capture vintages, which matters because a current
minute can change on a later response. `--refresh` explicitly appends a new
vintage. M3.2, not M3.1, will choose event-relative observations or calculate
latency/spread/execution features.

## Gaps and recovery

- An event without a stock code becomes a `missing_stock_code` gap without a
  provider call.
- A successful captured response with no rows becomes `provider_no_rows`.
- Transport, HTTP, provider, JSON, or semantic failures remain failed runs;
  any raw pages already committed remain visible.
- A restart marks interrupted runs failed and returns their targets to pending.
- Failed targets move only through explicit retry; completed targets move only
  through explicit refresh.
- Pagination moves backward from the real collection time (or 23:59:59 for a
  past date), never assumes a universal 15:30 close, and fails if the configured
  page bound is exhausted.

## Validation and limitations

Focused tests cover raw-first persistence, exact event/market timestamps,
idempotent registration, missing-symbol/empty gaps, wrong-date rejection,
retry, interruption recovery, multi-page traversal, future-target rejection,
append-only target protection, credential-free request provenance, CLI parsing,
and later-vintage refresh.

Focused, combined, safe-full, and unaffected-artifact suites passed `11/11`,
`53/53`, `408/408`, and `4/4`. The literal full run was `408 passed, 1 failed`
only because ignored `data/kdtb.db` still has the previously documented verifier
hash `4e387d5a…`, not the trusted M1.1 input hash `265d888a…`.

No KIS credentials were available, so official documentation and an exact HTTP
contract test establish capability, but no live provider response was captured.
No production target was registered. This milestone does not provide quotes,
midpoints, spreads, streaming ticks, fills, interpolation, historical data
beyond what KIS actually returns, or an event-relative dataset.

## Handoff invariants

1. Never normalize a provider page without first committing its exact bytes.
2. Never accept a parsed bar that cannot be re-derived from its retained page.
3. Keep DART source-date precision distinct from exact watcher observation time.
4. Treat empty results and missing symbols as data, not zeros.
5. Preserve every failed/partial run and every response vintage.
6. M3.2 may derive event-relative rows but must not rewrite M3.1 raw captures.

## Builder correction

The completion API no longer accepts `observations_seen`. `finish_run()` holds
an immediate write transaction, reconstructs every request, verifies every raw
hash, re-parses every retained response, and requires pages numbered from one in
a source-contiguous backward cursor chain. It compares the full canonical
storage tuple for every derived observation against the durable rows and only
then writes the derived count and terminal state.

This makes terminal facts evidence-backed:

- zero-capture runs cannot succeed;
- nonempty captures cannot become `provider_no_rows` merely because a caller
  claims zero observations;
- unnormalized or inconsistent bars prevent completion;
- `provider_no_rows` requires exactly one parsed empty first page;
- a full last page cannot silently end while another in-date cursor remains.

Capture persistence and normalization also acquire a write lock and recheck
both the run and target state. Once completion commits, later normalization is
rejected. A completion/normalization race therefore cannot add a bar behind an
immutable empty-result gap.

The strict parser now rejects `output2` arrays longer than the documented 120
rows. The regression sends 121 valid provider-shaped rows through the normal
collector: exact bytes remain retained, the run fails, and zero bars are stored.
Additional direct regressions exercise captureless completion, a retained
nonempty but unnormalized page, store-derived counts, and terminal lifecycle.

Focused, combined, unaffected-artifact, and safe-full suites pass `13/13`,
`55/55`, `4/4`, and `410/410`. The literal full suite remains `410 passed, 1
failed` solely because ignored `data/kdtb.db` still has hash `4e387d5a…` rather
than the trusted M1.1 hash `265d888a…`. Scoped Black, compilation, CLI/import,
diff, SQLite integrity, and foreign keys pass. The database hash did not change;
no research logic or artifact was modified. M3.1 is `AWAITING VERIFICATION` and
M3.2 remains `NOT STARTED`.

## Independent re-verification after terminal-state correction

The original verification attacks are closed. Completion rejects missing raw
captures and nonempty unnormalized captures, derives the stored count, and
prevents later normalization. A 121-row page fails before bar persistence while
its exact raw bytes remain durable.

Two surrounding terminal invariants remain open. First, the reconciled page
chain has no durable initial cursor. A verifier claimed a run at 07:00 UTC
(16:00 KST), persisted and normalized a short first page requested only through
09:00 KST, and completed successfully with one observation. Inter-page cursor
checks and the terminal short-page check passed, but the durable result omitted
the rest of the intended collection window.

Second, completion does not require its timestamp to follow retained provider
traffic. An empty response requested at 07:02 UTC and received at 07:03 was
completed with both `finished_at` and its `provider_no_rows.recorded_at` at
07:01. The run was `succeeded`; SQLite integrity and foreign keys passed. A
terminal state therefore can predate the source evidence said to justify it.

Focused, combined, unaffected-artifact, and safe suites passed `13/13`,
`55/55`, `4/4`, and `410/410`; the literal full suite remained `410 passed, 1
failed` only for the known ignored-database hash mismatch. Scoped formatting,
compilation, CLI/import, diff, SQLite integrity, and foreign keys passed, and
the database remained `4e387d5a…`.

M3.1 returns to `IN PROGRESS`. A run needs a durable initial-cursor fact that
completion can verify, and terminal times must be no earlier than run start and
all retained request/response times. M3.2 remains `NOT STARTED`.

## Builder initial-boundary and chronology correction

The initial boundary is now an explicit run fact. At claim time the store derives
the first KIS through-time from the target date and exact UTC start: current-date
targets use the corresponding KST wall time truncated to seconds, while past
targets use `23:59:59`. It persists that value as `initial_cursor`, returns the
same value to the collector, and protects run ID, target, start, and cursor from
updates. An idempotent migration adds the column and identity trigger to earlier
M3.1 schemas; any unfinished legacy run without a cursor fails closed.

Completion independently derives the expected cursor from the immutable target
and stored start, checks the frozen value, and requires the first retained
request to use it before evaluating inter-page continuity. Thus a run claimed at
07:00 UTC/16:00 KST cannot complete from a short page requested only through
09:00 KST.

All terminal transitions now share the retained-evidence chronology invariant.
A success, explicit failure, or interrupted-run recovery timestamp must be no
earlier than the run start and every stored request and response time. The check
runs under the same immediate transaction as terminalization. Because a no-row
gap uses the accepted completion timestamp, it cannot predate its source bytes.

Direct regressions replay both verifier attacks. The 09:00 page remains retained
but cannot terminalize the 16:00 run. An empty response requested at 07:02 and
received at 07:03 rejects completion at 07:01 without writing a gap; completion
at 07:03 succeeds and the canonical gap records exactly 07:03. The tests also
prove the frozen cursor rejects database updates.

Focused, combined, unaffected-artifact, and safe-full suites pass `15/15`,
`57/57`, `4/4`, and `412/412`. The literal full suite remains `412 passed, 1
failed` solely because ignored `data/kdtb.db` has hash `4e387d5a…` rather than
the trusted M1.1 hash `265d888a…`. Scoped Black, compilation, CLI/import,
legacy-schema migration, diff, SQLite integrity, and foreign keys pass. No
research logic, artifact, or ignored-database byte changed. M3.1 is `AWAITING
VERIFICATION`; M3.2 remains `NOT STARTED`.

## Independent re-verification after chronology correction

The prior two attacks are closed. The first retained request must use the
frozen cursor, run identity cannot be updated, and success, failure, and
recovery reject terminal timestamps earlier than their run or retained provider
traffic. The legacy migration also adds the nullable cursor column and identity
trigger without rebuilding existing tables; new runs populate it, while
completion rejects a missing cursor.

A separate cross-record chronology attack still succeeds. A canonical event was
normalized at 00:01 UTC and its immutable market-data target registered at
00:02. Calling the public store boundary with a 00:00:30 claim produced a frozen
cursor and running row. A verified empty request/response at 00:00:40/00:00:50
then completed at 00:00:55 and wrote a `provider_no_rows` gap at that time. The
run, response, success, and gap all predate the target registration; the run
also begins before canonical normalization. SQLite integrity and foreign keys
remain clean because `claim_next()` checks the target date but not its
`registered_at` or event chronology.

The collector's normal clock calls are ordered, but the durable store accepts
the contradiction and therefore cannot guarantee truthful state across clock
rollback, direct service use, or replayed timestamps. Claiming must reject a
start before the immutable target exists (which also follows its normalization),
and terminal paths must retain that invariant. A direct regression should prove
that no run or gap is written for the attack.

`57/57`, `4/4`, and `412/412`. Literal full remained `412 passed, 1 failed`
only for the known ignored-database input hash. Scoped Black, compilation,

## Builder target-to-run chronology correction

`claim_next()` now compares the requested UTC start with the immutable target's
`registered_at` before it derives a cursor or changes state. A start earlier
than registration raises and rolls back the immediate transaction, leaving the
target pending with no attempt, run, capture, or gap. Exact-registration starts
remain valid. Since target validation already requires `registered_at >=
event_normalized_at >= event_observed_at`, this one boundary orders the run
after the complete durable event lifecycle rather than duplicating weaker
comparisons.

The common terminal chronology guard independently reloads the canonical target
and applies the same comparison to the stored run start before checking success,
explicit failure, or interrupted-run recovery against provider evidence. This
is intentionally redundant with claim-time validation: a legacy impossible run
from the earlier implementation fails closed and cannot be converted into an
apparently truthful terminal state.

Direct regressions reproduce the verifier's 00:00:30 claim against a target
registered at 00:02 and prove zero runs/gaps plus unchanged pending state. A
second regression injects the kind of legacy pre-target running row that could
already exist and proves recovery rolls back without terminalizing it.

Focused, combined, unaffected-artifact, and safe-full suites pass `17/17`,
`59/59`, `4/4`, and `414/414`. Literal full remains `414 passed, 1 failed`
