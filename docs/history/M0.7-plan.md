# M0.7 plan — Historical data-readiness audit and ML gate

**Planning status:** awaiting independent review  
**Date:** 2026-10-02  
**Scope:** audit and decision only; no source repair, model training, database
migration or M3.2 work.

## Why this gate comes before ML

M0.6 repaired learner chronology, but it deliberately left the source cohort
unchanged. A chronologically correct learner can still learn from invalid event
populations, retrospective issuer metadata, later corrections or price windows
that did not exist at decision time. Increasing model complexity would make
those defects harder to diagnose.

The required next question is therefore not which model performs best. It is
whether the available event, security and outcome evidence supports a
point-in-time training row at all.

## Read-only inventory

The seven primary category CSVs contain 28,979 category-row copies and 28,737
unique receipt numbers from 2021-06-28 through 2026-06-24. They contain 242
cross-category receipts: 230 overlap bonus-issue and halt-resumption filters,
and 12 overlap convertible-bond and rights-offering filters. These are shared
events, not independent samples that may be separated across folds.

Four overlaps have divergent frozen copies and category-dependent admission:

- `20220509900146` is missing/fetch-failed in bonus issue but valid in halt;
- `20230921900106` and `20230926900688` have T+5 values in bonus issue but not halt;
- `20250124900682` has T+5 in rights offering but not convertible bond.

No current input proves which category copy should be canonical. M0.7 must retain
both, report field-level differences and keep row-copy counts separate from
unique receipt counts. The 28,670 admitted copies represent 28,432 receipts with
at least one admitted copy and 28,428 receipts whose every copy is admitted.

double-counting either as an independent-event population.

`MarketDataClient.event_returns` selects the first available stock row on or
after the event date without a maximum gap. In the retained files, pre-listing
or otherwise unavailable securities can therefore acquire a T0 price much
later. The largest observed delay is 1,341 calendar days. This invalidates the
affected rows and demonstrates that a historical listing interval is required.

## Source boundaries

### Security identity

There is no effective-dated security-master file or table. The event CSVs carry
one DART-derived corporation code, stock code and market value, but all were
captured retrospectively. They do not prove listing status, market, share class
or tradability on the filing date. The corpus also contains alphanumeric
six-character stock codes while some prospective schemas accept digits only.

The official OPEN DART list interface exposes filing date, corporation type,
corporation code and stock code. Its corporation-code snapshot includes a
`modify_date`; neither interface is an effective-dated KRX listing history.
KRX Data Marketplace advertises current issue information plus new-listing and
delisted-issue datasets, which makes an authoritative reconstruction worth a
separate source-feasibility milestone. M0.7 will not fabricate that history.

### Price windows

The frozen category files retain T0/T+1/T+2/T+5 closes and returns. They do not
retain the raw daily OHLCV response, response hash, capture time, request
boundary or volume. Their dates were backfilled later while preserving the old
closes, so date provenance and price-vintage provenance can differ.

M0.4 established that the route is a retrospectively adjusted Naver series via
pykrx and that later corporate actions can revise historical absolute closes.
The frozen values remain valid evidence of what earlier research consumed, but
they are not an auditable raw-bar source or executable-price record.

### Disclosure availability and lineage

The immutable buyback filing-time input covers 3,604 of 4,846 rows. It includes
52 pre-open filings, 1,703 filings from 09:00 through 15:29, 11 at exactly
15:30, and 1,838 after 15:30. A filing at or after the close cannot justify the
same-day close as an executable entry. The remaining 1,242 rows have no pinned
exact time.

The pinned audited inputs do not supply original report bytes, relationship
captures or contemporaneous observation timestamps. M0.7 must report these as
`not_supplied_by_pinned_inputs`; it must not query or scan the current database
to infer their presence or absence. The database is outside the audit boundary
and retains its separate known hash blocker.

### Intraday execution

The implemented KIS path is prospective and has a bounded historical lookback.
It cannot reconstruct 2021–2025 spreads, latency, order-book state or fills.
Historical intraday execution must remain unavailable; M3.2 and later forward
collection are the correct place to build new evidence.

## Planned artifact and decision rule

`historical_data_readiness_v1.json` will consume and pin all seven category
CSVs, the benchmark CSV and metadata, the buyback filing-time CSV, and any prior
artifact whose provider conclusion is copied into machine output. It will hash
every imported generator source and contain:

- input and generator-source hashes;
- category and unique-receipt populations;
- stable cross-category overlap identities, every category copy and field-level
  conflicts;
- daily-window admissions, ordered primary exclusions and nonexclusive defect
  flags;
- maximum and representative delayed-T0 cases;
- price, security, filing-time and lineage evidence matrices;
- buyback filing-time coverage and mutually exclusive time buckets;
- an explicit ML gate with stable blocker reason codes;
- the next bounded data milestone recommended by the evidence.

For the existing frozen cohort, the gate returns `GO` only when every
M0.6-admitted row copy has all three evidence pillars:

1. `point_in_time_security_identity`: a source-hashed effective-dated mapping of
   corporation, security code, market, instrument type, listing/delisting
   interval and trading eligibility on the event date;
2. `point_in_time_disclosure_evidence`: exact document-version bytes, source
   identity, lineage and an availability time no later than feature use;
3. `versioned_daily_label_source`: source-hashed raw daily bars with provider,
   capture time, request boundary and explicit adjustment policy.

Stable gate codes are:

- `missing_point_in_time_security_identity`;
- `missing_point_in_time_disclosure_evidence`;
- `missing_versioned_daily_label_source`;
- `cross_category_copy_conflict`.

Any present code produces `NO_GO`. `historical_intraday_unavailable_prospective_only`
is informational and reported separately; it is never substituted for daily
label evidence.

## Expected implementation boundary

The Builder should add one deterministic audit script, its versioned artifact,
targeted tests and a detailed M0.7 record. The script must use only pinned local
files, make no network or SQLite connection, and refuse modified inputs. Tests
should attack tampered hashes, missing columns, input permutations, delayed T0
windows and overlap accounting. Historical data and prior artifacts remain
immutable.

The Verifier should independently reconstruct headline counts from CSV lexemes,
inspect the four conflicting overlaps and longest delayed windows, challenge the
evidence matrix and GO / NO GO rule, force database/network failures, regenerate
the artifact to a fresh safe path byte-for-byte, and confirm that no source or
earlier research artifact changed.

## Independent plan review

The first review returned this plan before implementation because it treated
cross-category receipts as if their copies were identical and presented ordered
primary exclusions as a complete defect census. The corrected plan now makes
both distinctions explicit, limits reconciliation to frozen CSV lexemes,
freezes gate evidence and codes, and enumerates the no-DB/no-network boundary.

## Decision after M0.7

A `NO_GO` result does not end the ML branch. It defines the next work precisely:
first establish effective-dated security identity and a versioned daily outcome
source for one category, beginning with buybacks. Transformer-derived document
features should wait until original document versions and availability are
captured. Model training should wait until the resulting rows pass the gate.
