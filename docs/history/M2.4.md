# M2.4 — Forward reporting

## Objective

Report historical context and genuinely prospective results side by side without
pooling them, hiding rejected observations, or turning missing forward evidence
into a return estimate. This milestone is reporting only: it does not register
an experiment, evaluate an individual outcome, or authorize execution.

## Source boundary

`ForwardReportService` reads one exact activated M2.1 experiment version plus
its immutable M2.2 decisions and M2.3 outcomes through their existing validating
ledgers. The report cutoff is an explicit UTC `as_of`; records stored after that
cutoff are excluded. A service-clock `generated_at` proves the cutoff is not in
the future. Each report embeds the complete included source records, the exact
experiment definition/hash/activation, and separately derived historical,
forward, and frozen-evaluation sections.

Canonical report validation re-derives every aggregate from the embedded source
records. It rejects changed counts, returns, coverage, rejection summaries,
uncertainty, or evaluation results. Outcome-to-decision identity, hash,
experiment, issuer, rule, benchmark, cost, disposition, and recording chronology
are reconciled again at the report boundary.

The `forward-report` CLI opens the configured SQLite file through URI
`mode=ro`. It never calls `init_db()`, runs migrations, or writes a stored report.
Text and canonical JSON are deterministic for the same ledger state, cutoff,
and generation instant.

## Non-blended samples

The historical section is explicitly labeled `HISTORICAL — NOT FORWARD`. It
unions and receipt-deduplicates M1.4 comparable outcomes embedded in decision
contexts, then admits only rows whose exit date is strictly before the frozen
historical-cutoff date in Seoul. Conflicting copies fail. This is historical
context, not a replay of the experiment's eligibility rules, and the report
states that limitation. A compatibility label says whether the frozen M2.1
entry/exit, benchmark, and cost assumptions match the verified M1.4 basis.

The forward section is explicitly labeled `FORWARD — PROSPECTIVE ONLY`. It uses
only M2.3 outcomes linked to included eligible decisions. No observation or
return crosses between the two sections, and the top-level schema fixes
`historical_and_forward_are_combined=false`.

## Coverage, uncertainty, and frozen evaluation

Forward coverage reports considered, eligible, rejected, realized, and
eligible-without-outcome decisions. Rejection codes are counted separately and
identified as potentially overlapping. Coverage denominators are the durable
ledger decisions, not the external disclosure universe.

Each nonempty sample receives its own descriptive return metrics. Mean abnormal
net return uncertainty uses the repository's deterministic event-weighted,
issuer-clustered percentile bootstrap with 10,000 draws and seed zero. With no
outcomes, metrics and interval bounds are `None` and the status is
`no_observations`; with one issuer, the interval status is
`insufficient_issuers`. Neither case is presented as a zero return.

Only metrics from the forward cohort recorded by the frozen evaluation end feed
the M2.1 evaluation plan. Before the forward start the status is `pre_start`;
before evaluation end it is `collecting` and non-final. Afterward, unresolved
eligible cohort decisions produce non-final `awaiting_outcomes`. Once resolved,
minimum event/issuer counts are enforced before classification. Missing metric
values produce `metric_unavailable`; otherwise all success conditions and any
failure condition are evaluated, with frozen failure precedence and an explicit
inconclusive state. Unsupported frozen metric names fail rather than being
guessed.

## Independent verification failure

The section boundary and arithmetic held. Historical context and forward
outcomes remain separately labeled and separately aggregated; source-record
tampering is rejected; coverage includes rejected, realized, and missing
outcomes; uncertainty is issuer-clustered; and empty or one-issuer samples are
not converted to zero estimates. The CLI also left the database main-file hash
unchanged and retained the `NO_TRADE` boundary.

The time boundary does not hold. `as_of` is caller-supplied, and there is no
trusted generation timestamp or service clock against which to validate it. On
2026-09-17 UTC, the verifier requested the frozen 2026-12-31 evaluation end for
an empty temporary ledger. The service returned `insufficient_data` with
`classification_is_final=true`, months before the claimed cutoff.

The meaning of final is independently unstable. The verifier built two
canonically valid reports for the same frozen experiment. At evaluation end,
one recorded outcome yielded final `insufficient_data`. A second outcome with a
valid January 2 recording time was then included by the later cutoff and changed
the still-final classification to `success`. This follows directly from
including outcomes through arbitrary `as_of` while setting finality solely from
`as_of >= evaluation_end`. Eligible decisions near the evaluation boundary can
legitimately mature afterward, so a final result cannot be claimed while those
outcomes remain unresolved unless the frozen specification supplies a terminal
missing/maturation policy.

Focused M2.4, combined M2.1–M2.4, unaffected artifact, and safe repository suites
passed `8/8`, `72/72`, `22/22`, and `395/395`. The separately run M1.1 artifact
test failed only because the ignored database still hashes to `4e387d5a…` rather
than `265d888a…`. Black, compilation, CLI/import, diff, immutable-read database
integrity, and foreign keys passed, and the database hash did not change.

M2.4 returns to `IN PROGRESS`. It needs a trusted generation-time boundary plus
a stable finalization rule and direct regressions. M3.1 remains `NOT STARTED`.

## Builder correction after verification failure

`ForwardReportService` now owns report time through an injected UTC clock,
defaulting to the real system UTC clock in production. It calls the clock once,
embeds that instant as `generated_at`, and rejects `as_of > generated_at` before
querying the ledgers. The schema also requires `as_of <= generated_at`, so a
canonical report cannot contradict its embedded chronology. The CLI exposes no
way to supply the service clock; manual clocks exist for deterministic tests.

Final evaluation now has a fixed cohort policy:
`decision.recorded_at <= evaluation_end`. Reports continue to show every ledger
decision through `as_of` in the overall forward section. The evaluation section
separately reports cohort decision/eligibility/rejection/outcome counts and the
receipt numbers of post-window decisions excluded from the verdict. Thus a
late-recorded decision is visible rather than silently lost, but cannot rewrite
the prespecified evaluation cohort.

Outcomes for cohort decisions remain admissible after evaluation end because
the frozen daily-close horizon may mature later. Until every eligible cohort
decision has a durable outcome, evaluation status is `awaiting_outcomes` and
`classification_is_final=false`. No timeout, imputation, or terminal-missing
policy was invented. Once all cohort outcomes exist, their one-per-decision,
append-only M2.3 boundary plus the closed decision cohort makes a final verdict
stable. Later post-window decisions can change observational coverage but not
the cohort metrics, criteria, or classification.

Direct regressions reproduce the verifier cases. With a September 17 trusted
clock, a December 31 cutoff fails. At December 31, one of two eligible cohort
decisions still lacks its January 2 outcome, so the report is non-final
`awaiting_outcomes`; after that outcome is recorded the verdict becomes final
success. A decision recorded January 3 remains visible as a post-window
exclusion while the same final success metrics and criteria are preserved.

  `397 passed`;

The verifier-altered ignored database remains `4e387d5a…`; no artifact was
re-baselined and research results did not change. M2.4 returns to
`AWAITING VERIFICATION`. M3.1 was not started.

## Independent re-verification

On 2026-09-17, independent checks reproduced the prior attack boundaries. A
cutoff one microsecond later than the trusted service time was rejected, and a
forged canonical report with `as_of > generated_at` failed validation. The
clock was read exactly once for a report.

The frozen cohort boundary also held exactly. A decision recorded at
`evaluation_end` was included and, without an outcome, produced non-final
`awaiting_outcomes`. A decision one microsecond after the boundary remained in
overall forward coverage but was explicitly excluded from evaluation and did
not change the completed cohort's metrics, criteria, or final success verdict.
No imputation, timeout, or terminal-missing path was found.

Focused M2.4, combined M2.1–M2.4, unaffected-artifact, and safe repository
suites passed `10/10`, `74/74`, `22/22`, and `397/397`. The literal full suite
reported only the pre-existing M1.1 input-hash mismatch (`397 passed, 1 failed`)
because the ignored database is still `4e387d5a…` instead of trusted
`265d888a…`. Scoped formatting, compilation, read-only CLI behavior, diff,
SQLite integrity, and foreign keys passed, and that database remained
byte-identical.

M2.4 satisfies its acceptance criteria and is `VERIFIED`. M3.1 remains
`NOT STARTED`.
