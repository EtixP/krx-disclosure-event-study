# M1.5 — Human-readable alert and historical replay

## Objective

Turn one immutable M1.2 event delivery into useful terminal research context
without adding a signal, forward experiment, execution path, dashboard, or LLM
prose generator. Live delivery and historical replay must use the same event
and alert core, while replay must preserve decision-time chronology.

## Structured alert boundary

`ResearchAlertBuilder` composes one `EventEnvelope` with the default verified
M1.3 `SignificanceEngine` and M1.4 `HistoricalContextService`. The immutable
`m1.5-v1` result retains:

- delivery/trigger identity, canonical event, processing time, and assessment
  cutoff;
- economically important contract value, prior revenue, and ratio fields
  derived only from validated M1.3 measurement state;
- significance status and its auditable population state;
- either an M1.4 result or a structured reason context is unavailable; and
- a fixed `NO_REGISTERED_STRATEGY` / `NO_TRADE` disposition.

The alert schema recomputes the default M1.3 assessment from the embedded event
and cutoff. It also checks displayed economic fields, missing fields, and any
M1.4 result against that same event and cutoff. Altering significance
explanation prose, a magnitude, displayed fields, context identity, or an
event-derived unavailability reason cannot produce a valid alert merely because
its shape remains valid.

`render_alert` uses fixed labels and validated numeric/status fields. It never
uses the free-form significance explanation and imports no LLM client. Missing
normalized inputs remain named; fields are not fetched, guessed, or converted
to zero by the presentation layer.

## No registered strategy

M2.1 has not defined or activated a frozen experiment registry. The repository
does contain legacy historical strategy code, but it is not a registered
prospective experiment. M1.5 therefore has exactly one truthful strategy state:

```text
NO REGISTERED STRATEGY
NO TRADE
```

This means no strategy or execution is authorized. It is not a forecast that a
trade would lose, and it does not convert M1.3 magnitude or M1.4 historical
context into a recommendation. Supporting registered experiment applicability
requires M2.1's versioned, immutable definitions and is intentionally not
implemented here.

## One live/replay path

`ResearchAlertConsumer` implements M1.2's `EventConsumer`. Live mode registers
it directly with `LiveDartWatcher`; historical mode calls
`LiveDartWatcher.replay` with the same consumer class. Both therefore share:

```text
raw disclosure / stored snapshot
    → M1.1 canonical event
    → M1.2 immutable snapshot and delivery journal
    → M1.3 significance + M1.4 context
    → M1.5 structured alert
    → deterministic terminal text
```

`LiveEventStore.receipt_nos_for_date` performs a sorted, optionally bounded,
read-only date selection. It does not create a second normalizer. Replay then
uses the existing watcher snapshot builder and delivery method. The delivery
journal skips a repeated `(consumer_name, trigger_receipt_no)` success; callers
must choose a new consumer name deliberately if they want a second delivery.

## Replay chronology and provider behavior

Live alerts assess at the snapshot's timezone-aware normalization time.
Historical alerts assess at the latest canonical source timestamp from M1.3's
shared chronology utility, never at the later replay-processing time. The
M1.4 strict Seoul-date cutoff then excludes same-day and future T+5 outcomes.
Date-only DART timestamps retain their documented Korean-local midnight
precision; M1.5 does not invent a filing time.

Existing snapshots and self-contained original raw receipts can replay without
an API key. An update receipt without already stored relationship evidence
still needs DART retrieval; offline replay fails that receipt visibly rather
than guessing lineage.

## Terminal interface

```bash
python -m kdtb.cli watch --once
python -m kdtb.cli watch --poll-interval 60
python -m kdtb.cli replay 2026-08-25
python -m kdtb.cli replay 2026-08-25 --limit 20
```

The package-module command is used instead of modifying `pyproject.toml`, which
is generator provenance for verified M0.4/M0.5 artifacts. This preserves their
immutable hashes while still providing the roadmap's watch/replay interface.

## Independent verification failure (2026-09-09)

The replay and presentation paths otherwise reproduced, but the alert's M1.2
delivery provenance is not semantically bound to its displayed event.
`ResearchAlert` checks only that `delivery_id` contains 64 hexadecimal
characters. Starting from the real M1.2 ID derived from the trigger receipt and
canonical event hash, the verifier replaced `corp_code`, `corp_name`, and
`stock_code` while retaining that original ID. The altered alert passed JSON
validation and rendered the forged issuer.

The validator must recompute or call a shared M1.2 delivery-identity function
over the exact trigger and embedded event snapshot. Direct regressions should
cover an issuer/event substitution, an arbitrary valid-looking ID, and changing
the trigger within a multi-receipt event. This is a provenance failure, not an
argument for adding a strategy or M2.1 behavior.

Historical source-time behavior held independently. For an event processed in
2026 but filed on 2025-01-20, live assessment selected 3,091 comparable outcomes
while historical replay selected 3,085 and excluded all six outcomes unavailable
at the filing cutoff. Direct/focused/full suites passed `10/10`, `108/108`, and
`321/321`; Black, compilation, CLI smoke, and diff checks passed. M0.4, M0.5,
and M1.1 regenerated byte-for-byte at `1acf9366…`, `3677a4c2…`, and
`33ff2517…`; upstream hashes and research conclusions remained unchanged.

M1.5 returns to `IN PROGRESS`. M2.1 was not started.

## Builder correction after verification failure

The M1.2 canonical serialization, event SHA-256, and delivery-ID formula now
live behind one shared identity module. `LiveEventStore` uses it when persisting
the immutable snapshot, `LiveDartWatcher` uses it when deriving the delivery
key, and `ResearchAlert` recomputes the same key from its embedded event and
trigger during validation. The delivery formula and existing IDs did not
change; the previously implicit relationship is now an enforced invariant.

Direct adversarial tests begin with a valid alert and reject:

- replacing all three displayed issuer identifiers while retaining the old ID;
- replacing the ID with an arbitrary shape-valid 64-hex string; and
- replacing the trigger with another receipt that genuinely belongs to the
  same multi-receipt event while retaining the old ID.

The existing live/replay integration passes watcher-derived IDs through the
same validator, preventing a test-only identity convention from masking drift.
Direct M1.5 tests passed `13/13`; the focused suite passed `111/111`; the full
suite passed `324/324`. Black, compilation, CLI smoke, and diff checks passed.
M0.4, M0.5, and M1.1 regenerated byte-for-byte at `1acf9366…`, `3677a4c2…`, and
`33ff2517…`, respectively. No research result changed.

M1.5 is `AWAITING VERIFICATION`. M2.1 was not started.

## Independent re-verification (2026-09-10)

The verifier independently reconstructed the pre-refactor M1.2 canonical JSON,
event SHA-256, and `m1.2:{trigger}:{event_sha256}` delivery formula. The shared
identity functions produced byte-identical hashes. Starting from a valid
multi-receipt alert, forged issuer fields, an arbitrary shape-valid ID, and a
different valid related trigger with the stale ID all failed validation. The
related trigger succeeded only after deriving its own identity, and ordinary
JSON round-trips remained valid.

The delayed-processing chronology check again selected 3,091 live outcomes and
3,085 replay outcomes, excluding exactly the six outcomes not knowable at the
filing cutoff while retaining the same delivery ID. Direct, focused, and full
suites passed `13/13`, `111/111`, and `324/324`; Black, compilation, CLI help
smoke, and diff checks passed. M0.4, M0.5, and M1.1 regenerated byte-for-byte,
and all verified upstream artifact hashes remained unchanged.

M1.5 is `VERIFIED`. M2.1 was not started.
